# Serf Production Plan

> One working solution. No versioning, no speculative architectures. Serf becomes a utility: install once, run in any project, and the harness improves the project autonomously.

## The Goal

Serf is an **actor-critic harness for coding agents**. The master reads the project state, talks with the user, writes tasks to a board, and spawns serfs to execute them. Each serf has an identity (mission, persona, lever, measurement, fate). A separate critic adversarially evaluates output. Work is isolated in git worktrees. Knowledge compounds in `.serf/knowledge/`.

The long-term vision is a **self-improving dark factory**: curiosity generated by disagreement or friction drives the system to investigate, optimize, and even evolve its own methods. But first, the harness must work.

Success criteria for v1.0.0:

1. `bun install && bun run build && bun link && serf init && serf start` works in a fresh repo.
2. The master serf talks with the user, surveys the project, and writes well-specified tasks.
3. Actor serfs execute tasks autonomously and write results.
4. The critic adversarially evaluates output against evaluable acceptance criteria.
5. Work is isolated in git worktrees; failures are discarded, successes merged.
6. Knowledge compounds: skills, patterns, and failures accumulate.
7. The system respects budget limits and does not tokenmaxx.
8. One branch on git: `main`.

## Strategic Principles

- **Start with herdr.** Direct mode via tmux/shell was fragile. herdr provides real pane management and state detection. Once herdr mode is solid, we can revisit a simpler direct mode.
- **Master is a serf identity.** `master.md` has its own mission/persona/lever/measurement/fate. The CLI launches the user's coding agent as the master.
- **Goal + lever on every card.** Each task has a clear `## Goal` (the single done condition) and `## Lever` (the action the serf should take). This mirrors Karpathy's autoimprove and helloh autoimprove patterns.
- **Friction is curiosity.** When the actor and critic disagree, or when the system detects a gap in its own capability, that friction becomes a signal to investigate — not just retry blindly. Schmidhuber's artificial curiosity: prediction error = attention.
- **Rings of strategy.** The harness has explicit strategy rings that can be enabled per task:
  - `autoimprove` — the system proposes improvements to its own process
  - `autoresearch` — investigate before executing
  - `evolutionary` — generate variations, tournament/select
  - These are opt-in per card; the default ring is simple actor-critic.
- **No CLI dialogue.** The coding agent (Claude Code, opencode, etc.) is the conversational interface. The CLI only launches it.
- **Package managers only.** The actor installs dependencies only via the project's package manager. `uv` is the preferred Python tool. No `curl | bash`, no global installs, no system directories.
- **Containerization without Docker (future).** Once worktrees are solid, add opt-in container isolation using Apple Container (macOS-native Linux containers in lightweight VMs) or the NanoClaw pattern (per-agent containers with explicit mounts and credential proxying). Docker is not the default.
- **One working solution.** All speculative plans and old architectures are archived.

## What We Will NOT Do

- No more parallel architectures (`v2/`, `v3/`, etc.).
- No more writing long plans before implementing.
- No more tmux-first direct mode. herdr is the substrate for now.
- No more cloud-provider failover megaplan. One LLM backend that works.
- No more TUI. The agent's own UI is the interface.
- No more container isolation plans. Worktrees are enough.

## Phase 1: Harden herdr Mode + Project-is-Config (in progress)

### 1.0 Project is the Config ✅

All serf configuration and state lives in the project's `.serf/` folder. Serf never writes to `~/.serf/`, `~/.config/`, or system paths to configure itself. Capability detection is read-only and reported to the user and the coding agent.

Acceptance:
- `~/.serf/` removed; config lives in `.serf/config.json`.
- `~/.config/ghostty/config` restored and untouched by serf.
- `serf .` initializes and starts in one command.

### 1.1 Package Manager Discipline

The harness must enforce that agents only use project-local package managers. This is a security and reproducibility rule, not just a prompt suggestion.

Rules baked into actor and critic prompts:
- Detect the project's package manager from files in the worktree (bun/npm/pnpm/yarn for JS; uv/pip/poetry for Python; cargo for Rust).
- For Python, prefer `uv` when `pyproject.toml`, `uv.lock`, or `requirements.txt` exists.
- Install dependencies only via that package manager, locally.
- Never run `curl | bash`, `wget | sh`, `sh -c`, or remote scripts.
- Never write to `~/.ssh`, `~/.config`, `~/.local`, `/usr/`, `/opt/`, or any system directory.
- Never use `sudo` or global installs.
- If a required tool is missing, the actor adds it to the project manifest or asks the master to scope it.

Future: a pre-execution check script scans the worktree for forbidden commands before the actor starts.

Acceptance:
- Actor prompt contains the package-manager rules.
- A test verifies a mock shell command is rejected if it uses `curl | bash`.

### 1.1 Fix the agent launcher (`src/v2/executor.ts`)

The launcher shells out with `$(cat 'promptFile')`. This breaks on quotes and long prompts. Replace with safe invocation patterns:

- `claude --prompt-file <path> --output-file <path>` (or equivalent)
- `opencode run --prompt-file <path> --output-file <path>`
- `aider --message-file <path> --yes-always`
- Each agent writes output to a sentinel file and exits.
- If an agent does not support headless file-based I/O, mark it `interactive` and require user action.

For herdr mode specifically, use herdr's `sendCommand` and pane output capture rather than launching a separate terminal.

Acceptance:
- A mock-agent test verifies prompt file is passed correctly.
- `serf start` with herdr running produces actor output without hanging.

### 1.2 Real serf identities

`master.ts` currently passes a hardcoded empty identity to `buildAgentPrompt`. Load `.serf/serfs/actor.md` and `.serf/serfs/critic.md` from disk. Add `.serf/serfs/master.md` on `serf init`.

Master identity:
```markdown
## Mission
Orchestrate the dark factory. Survey the project, talk with the user, write tasks, spawn serfs, ensure convergence.

## Persona
Clear, strategic, autonomous. Asks good questions. Writes evaluable goals and levers.

## Lever
- .serf/ folder (board, knowledge, identities, events)
- User conversation
- callLLM for classification and planning

## Measurement
- Tasks written per session: >0
- Tasks that pass critic: >70%
- User refinement rate: <30%

## Fate
If the factory is confusing, my protocol is wrong, not me.
```

Acceptance:
- `buildAgentPrompt` uses the loaded `SerfIdentity`.
- Tests verify prompt contains mission/persona/lever from `actor.md`.

### 1.3 herdr harness end-to-end

`HerdrHarness.create` currently creates a workspace, launches actor in the root pane, and optionally a critic pane. Harden:

- Detect herdr availability at startup. If not running, print clear instructions and exit.
- Actor pane: launch with the actor identity and task prompt.
- Critic pane: launch with critic identity. If unavailable, fall back to inline LLM critic.
- Use herdr's pane output capture to read actor output reliably.
- Support dialogue between actor and critic panes for convergence.

Acceptance:
- A test with a fake herdr socket verifies pane creation and command sending.
- A real run in the serf repo completes a simple task end-to-end.

### 1.4 Worktree discipline

Current worktree creation/merge/discard silently swallows errors. Fix:

- Report worktree failures clearly.
- Only merge if the worktree has a clean, non-empty diff.
- On merge conflict, move card to `review/` and preserve context.
- Add `.serf/worktrees/` and `.serf/workspaces/*/` to `.gitignore`.

Acceptance:
- Tests for create/merge/discard success and failure.
- A passing task leaves a clean merge commit. A failing task leaves no trace in `main`.

### 1.5 Config cleanup

One global config: `~/.serf/config.json`. Defaults:
```json
{
  "agent": "claude",
  "model": "claude-sonnet-4-20250514",
  "backend": "anthropic",
  "terminal": "ghostty"
}
```

Acceptance:
- `serf config show` works with no config (shows defaults).
- `serf agents list` marks installed agents.

## Phase 2: Make the Critic Loop Trustworthy (2 days)

### 2.1 Goal + lever on every card

Update card schema to require:

```markdown
## Goal
The single condition that means the task is done.

## Lever
The action or method the serf should use.

## Acceptance
- Criterion 1 (evaluable)
- Criterion 2 (evaluable)
```

`addTask()` and the master prompt generate these fields.

Acceptance:
- All new cards have Goal and Lever.
- `validateCard` rejects cards without evaluable acceptance criteria.

### 2.2 Criterion-based critic, no self-confidence

`critic.ts` already parses YES/NO/CANNOT_EVALUATE. Keep it. Confidence is derived from answers. The legacy format fallback stays until proven unnecessary.

Acceptance:
- Bad output fails with specific criterion evidence.
- All critic tests pass.

### 2.3 Effort levels on cards

Add `## Effort` field: `quick` (1 pass), `standard` (3 passes), `thorough` (5 passes). Default `standard`.

Acceptance:
- `quick` tasks use one critic pass.
- Tests cover all effort levels.

### 2.4 Curiosity handling

Current code logs curiosity to `knowledge/patterns/` and retries. This can loop. Change:

- First curiosity: retry once with curiosity notes as feedback.
- Second curiosity on same card: spawn an **investigator serf** with limited budget to research the curiosity.
- Investigator writes findings to `knowledge/references/`.
- Actor and critic retry with the findings.
- If still curious: move to `review/` for user decision.

This is the first strategy ring: `autoresearch`.

Acceptance:
- A test simulates curiosity → investigator spawned → retry → converge or review.

### 2.5 Critic reads knowledge

Inject latest 3 skills, 3 failures, and 3 patterns into the critic prompt before evaluation.

Acceptance:
- Test verifies knowledge snippets appear in critic prompt.

## Phase 3: Knowledge Compounds (1 day)

### 3.1 Actor writes knowledge on completion

After pass, the actor must create or update a skill in `knowledge/skills/`. After fail, write a failure in `knowledge/failures/`. The master loop checks this and prompts if missing.

Acceptance:
- Passing task creates skill file.
- Failing task creates failure file.

### 3.2 Knowledge summary in prompts

Load latest knowledge into actor and critic prompts.

Acceptance:
- Test verifies skills/failures appear in prompts.

### 3.3 Retire stale serfs

If a serf has no task for 7 days, deprecate it. Use existing `deprecateSerf`.

Acceptance:
- Test verifies deprecation based on `lastActivity`.

## Phase 4: Strategy Rings (2 days)

Strategy rings are opt-in modes declared on the card:

```markdown
## Strategy
autoimprove
```

Default ring is empty (plain actor-critic). Implemented rings:

### 4.1 `autoresearch`

When curiosity persists, spawn an investigator serf. Already described in 2.4.

### 4.2 `autoimprove`

After a task completes, the master asks: "What about this process could be improved?" It writes a meta-card to improve the harness itself (prompt, identity, threshold). This is how the system programs itself.

Acceptance:
- A completed task triggers a meta-card in backlog.
- The meta-card is processed like any other task.

### 4.3 `evolutionary` (future, sketch only)

For taste-based or optimization tasks, spawn multiple serfs with different approaches, run a tournament critic, and select the winner. Not implemented in v1.0; keep the ring reserved.

## Phase 5: Master Dialogue and Task Intake (1-2 days)

The master serf runs inside the user's coding agent. Its job:

1. Read `.serf/plan.md`, `.serf/knowledge/`, and the project structure.
2. Summarize the project and current board state.
3. Ask the user: "What would you like to work on?"
4. From the user's answer, write a card with Goal, Lever, Acceptance, Effort, Strategy.
5. Put it in `backlog/`.
6. The master then runs the loop: spawn actor in worktree, spawn critic, converge, merge/discard, write knowledge.
7. After completion, ask "what's next?"

The CLI `serf start` just launches the user's agent with the master prompt.

Acceptance:
- A fresh repo with `serf init` can have a task written by the master and executed by the actor-critic loop.

## Open Questions

1. herdr installation: do we bundle install instructions, or auto-install when missing?
2. Default agent: `claude` requires Claude Code. Should serf auto-detect installed agents and pick the first available?
3. Should the master loop run forever, or should `serf start` default to one task and require `--loop` for continuous?
4. Investigator serf budget: fixed (e.g., 10k tokens) or a fraction of the parent task's budget?
5. When a card has `strategy: autoimprove`, should the meta-card be auto-approved or shown to the user?

- `serf init && serf start` in a fresh repo leads to master dialogue, task writing, actor-critic execution, and a merged or discarded worktree.
- herdr mode completes at least one real task in serf and one in a foreign repo.
- All tests pass.
- README and SERF.md describe exactly what works.
- No active stale `v2/`, plan, or PRD files.
- Repo is on `main` and tagged `v1.0.0`.
